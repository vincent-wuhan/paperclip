# Multica + Paperclip 桥接定位

Date: 2026-10-31
Supersedes: `2026-10-28-multica-paperclip-local-deployment-handoff.md`（部署与安全细节仍有效，见文末引用）

## 出发点：业务层的有效积累

Multica 聚焦 tasks，对业务流没有好的沉淀与体现。实际使用中的痛点：

- **决策不是一等公民**："为什么这样做"只存在于 issue 评论串和 chat 里。chat 易失，评论随 issue done 沉底归档。三个月后问"当时为什么砍掉雷达板块"，答案埋在某个 issue 的第 N 条评论里。
- **时间轴是 issue 级的，不是业务级的**。产品形态的阶段演进（何时从 A 定位转向 B、何时立了分发业务线）没有实体承载。
- **property 捕获操作状态而非 rationale**。`wechat.media_id` 记录"发了什么"，不记录"为什么发、目标是什么、放弃了什么备选"。
- **issue 生命周期与业务生命周期错位**。业务线长周期，issue 短周期；done 即归档意味着业务知识被持续冲刷进档案堆，而非累积成资产。

这不是 Multica 的缺陷——它就是为 sprint 式协同执行设计的。是**业务记忆这个层它结构上不提供**。

**Paperclip 的定位：业务账本与决策面。** 留下"为什么发生"（决策史与阶段史）；Multica 留下"发生了什么"（执行史）。桥是让"为什么"被结构化沉淀的漏斗。

## 总体分工

| | Paperclip（本地） | Multica（云端 opc.yueming.xin） |
| --- | --- | --- |
| 角色 | 流程/业务控制面、决策面、业务账本 | 执行层：软件开发协同与执行 |
| 擅长 | 轻量处置流程、审批门、决策记录、出口插件 | squad/agent 协同、repo、任务实施、autopilot |
| 数据 | 决策记录、产品阶段时间轴、需求溯源、进度里程碑 | issue、评论、执行日志、任务状态 |
| 插件体系 | 有（packages/plugins、adapters、MCP） | 无（只有 skill/repo/agent/autopilot 挂载） |

## 四通道桥模型

```
              ┌─────────────────────────┐
              │  Paperclip（决策/账本面） │
              └───────────┬─────────────┘
    ① 进度上行（只读聚合）  │  ② 需求下行
  projects/issues/squad → │  ← 创建 issue 指派给接口人 agent
                           │
    ④ 决议回传（评论/状态） │  ③ 决策上行
  人拍板后写回 Multica  ←  │  → 接口人创建带 needs-decision
                           │    标记的 issue，转为 Paperclip 待决策项
              ┌───────────┴─────────────┐
              │  Multica（执行面）        │
              │  接口人 agent：收需求、    │
              │  拆解、派 squad/agent     │
              └─────────────────────────┘
```

- ①②③④ 的消息载体都是 issue + 评论，不发明新协议，只靠语义标签区分。
- **接口人**：一个专用 Multica agent，收窄集成面。Paperclip 不需要理解 squad 结构、agent 能力，只对接口人说话；拆解与路由在 Multica 体系内完成。批量需求一律由 Paperclip 发出，接口人负责批量计划的制定与跟踪，并按固定格式回报批量进度（已生成数/总数、成本、产物引用清单、异常项）。
- 价值排序：③④（决策通道）是核心——决策账本的进料口；① 的产出给阶段时间轴打里程碑；② 每条带溯源链接，可从 Multica issue 一跳回到 Paperclip 决策/需求记录。

## 决策记录 schema

决策上行时接口人必须带结构化提案（非自由文本），保证账本记录质量不依赖拍板时的心情：

```
背景 / 选项（含放弃项）/ 建议 / 影响面 / 截止时间
```

人在 Paperclip 拍板即自动生成账本记录：何时、何背景、何选项、选了什么、依据。无需额外归档动作。

## 执行分层判据：交互密度 × 治理属性

```
               治理属性弱（错了可改）
                      │
   代码编译、测试、     │   视频渲染、批量
   日常巡检、数据抓取   │   转码等重计算
                      │
低 ───────────────────┼─────────────────── 高
   交互密度            │
                      │
   （agent 自主完成）   │   文案创作、视频创作、
                      │   发布动作
                      │
               治理属性强（对外不可逆）
```

- **高交互 × 强治理 → Paperclip**：创作迭代密度极高（一轮几十次微决策），下沉会让传输/交互成本指数放大；发布是对外不可逆动作，审批门必须在决策面。
- **低交互 × 弱治理 → Multica**：agent 自主执行。
- **边界注意**：判据是交互密度而非任务类型。"一次生成 50 条初稿供筛选"这类低交互高产出任务，批量生成部分下沉是对的，人只参与筛选交互。

## 单条与批量的发布分工

```
单条（精修件/人写文/新号冷启动/管线验证）
  创作不在 paperclip：人直接写，或 multica agent 创作（chat 交互迭代）
  成件进入 paperclip（人挂到 issue，或经通道①回传引用）
  paperclip 只做：收件 → 审核 → 子插件建草稿 → 确认 → 本地出站（经 edge 代理）
  不排产、不拆解、不做批次管理

批量（批量创作/批量投放）
  下桥：规格下行 → multica 生产+执行 → 引用回传 → paperclip 审批 → 发布下行
```

- **paperclip 不建创作运行时**：单条路径中 paperclip 只做"收件、审核、出口"，无需配置任何创作型 worker/agent、skill 或模型。创作能力无论单条还是批量都在 multica 侧沉淀；paperclip 的运行时只配运营型能力（合规预检、查重、健康分析、计划生成）。

- **单条不走批量管线**：创作可能仍在 multica，但 paperclip 侧不产生流程工单——issue 是稀缺的注意力资源，只留给需要"被看到"的经营对象（账号、计划、审批、里程碑）。
- **出口物理上两处，治理逻辑上一处**：凭据统一由账号资产台托管与签发（两条路径取同一个保险柜）；结果统一写 `dispatch-result` 事件流，健康面板与账本只认事件流，不区分路径。机械出站代码各自演进（子插件本已存在，multica 管线是新增能力）。
- 桥成为唯一出口的风险随之消除：单条发布不依赖桥的可用性；桥故障只影响批量。

## 批量场景：头尾交互、中间无人

已规划的批量场景及其切法：

| 场景 | 交互在哪 | 治理属性 | 归属 |
| --- | --- | --- | --- |
| 批量创作文案 | 头（写 prompt/策略）+ 尾（筛选） | 弱 | 生成下沉 Multica；策略与筛选留 Paperclip |
| 批量生成短剧 | 头（分镜/设定）+ 尾（选片/精修） | 弱 | 渲染管线下沉 Multica；精修（高交互）拉回 Paperclip |
| 批量投放 | 尾（审批） | 强（对外不可逆） | 审批留 Paperclip；投放执行借道 Multica 出口 |

**批量内容不可直接批量发出。** 批量生成弱治理，但批量发布是高危动作：账号风险不是均摊而是"最差那条决定全局"，一条违规/低质内容即可导致限流甚至封号。发布前必须过审批审核门，且审批粒度按内容风险分级：

- **逐条人审**：新账号、新内容形态、敏感选题——发布件逐条进入 Paperclip 待审队列。
- **规则豁免 + 抽检**：成熟模板、已验证选题线——可按规则（模板白名单 + 账号健康度）批量放行，但保留随机抽检比例；豁免规则本身的变更属于决策记录，入账本。
- **风控熔断**：账号出现限流/异常信号时，该账号的所有批量放行规则自动失效，回退逐条人审。

共性结构：人的交互只在两端（定规格、验收/审批），中间是低交互高产出管线。

> Paperclip 定义批量任务规格（选题策略、模板、分镜、投放参数）→ 通道② 下行给接口人 → Multica 批量执行 → 只回传引用与元数据（状态、数量、成本、缩略图）→ Paperclip 呈现筛选/审批界面 → 拍板后投放件再下行执行。

设计要点：

- **产物不过桥**。视频/文案本体留在执行侧存储，桥只传引用（URL/storage key）+ 元数据，避免桥退化为资产搬运管道。
- **筛选与精修是回拉，不是下沉**。选中的少数内容才进入 Paperclip 侧精修/发布流程。交互密度在哪里，工作面就在哪里。

## 视频/分发插件：留在 Paperclip

Multica 没有运行时插件体系，重 UI、重交互、带发布出口的能力挂不住。发布链路按"单条与批量的发布分工"一节执行：单条本地出站（经 edge 代理满足微信 IP 白名单）；批量经通道②下行由 Multica 出口执行。凭据与治理逻辑统一在 Paperclip（账号资产台签发、dispatch-result 事件流），决策与插件本体留在 Paperclip。

## 垂域扩张性：运营中台模式

paperclip 插件体系沉淀的不是"视频分发工具"，而是一套领域无关的垂域运营中台模式。四个通用构件：

```
① 账号资产台     账号/凭据/健康度/业务状态
② 审批风控门     分级审批、规则豁免、熔断、流水/决策账本
③ 出口路由       catalog + 事件体系（加平台 = catalog 加一行 + 子插件包）
④ 桥             四通道对接生产层（接口人模式通用）
```

开新垂域 = 领域子插件（出口适配）+ 领域规则包（审什么、豁免什么、熔断看什么信号），四个构件、账本、桥、issue 状态流全部原样复用。候选垂域：电商店铺（错误定价≈毁号，审批+熔断直接复用）、私域社群（群发 sop）、知识付费、外联触达（对外不可逆动作同构）。

两条工程约束：

- **contentpub 主插件的领域逻辑要克制**。它是未来 N 个垂域运营台的第一实例，"账号资产、审批门、豁免规则、事件流"必须做成与"内容发布"解耦的通用模块，模块边界按①②③④切，不按业务切。
- **账本 schema 用中性词**。决策记录与流水用"资产、动作、外部系统、风险信号"而非"内容/文章"——账本是跨垂域积累的资产，各垂域决策史长在同一条时间轴上。

### 运营交互增强（视频垂域的首个实例）

运营工作的节律是"日常巡检轮次 + 异常处置 + 周期复盘"，交互设计应贴合这个节律，而非 issue 流水的罗列：

| 视图 | 服务的运营动作 | 关键交互 |
| --- | --- | --- |
| 驾驶舱（首页） | 每日巡检：一眼看全账号健康、今日待审、在途批次、异常告警 | 状态卡片 + 熔断信号置顶，异常项点击直达处置 |
| 审批工作台 | 批量过审：一屏多件并排预览，快速分级 | 缩略图网格、键盘流（逐条 J/K 切换、A 批准/R 驳回/E 豁免）、豁免规则命中提示（"此件命中模板白名单，可批量放行"） |
| 排期日历 | 计划视角：各账号的发布排期、频控余量 | 日历/时间轴视图，拖拽调整投放窗口 |
| 账号卡片 | 账号处置：健康度、限流信号、冻结/解冻 | 健康状态机可视化，冻结即停授权签发 |
| 账本时间轴 | 周期复盘：决策史 + 发布流水按时间轴混排，可回溯"为什么" | 决策记录展开显示 背景选项/依据，流水折叠 |

优先级：驾驶舱与审批工作台是日常高频，先做；排期日历与账本时间轴是治理深度，随批量业务起量后补。

## 风险与对策（自媒体运营实操）

### 1. 多账号防关联 → 账号级出口策略（现阶段降级为预案）

关联风险分两类：**同平台多账号**（矩阵号，平台主动检测处罚——真风险）；**一人各平台各一号**（全网创作者常态，跨平台分发本是正当行为——无需防御）。出口策略的粒度是 平台 × 账号，不是"人"。

**现阶段（1 人 ≤2 账号、多平台、优先跑通全流程与产能验证）**：`browser-local` 单出口即够，不做代理池/严格隔离——过度设计会拖慢主线。仅保留两条纪律：同平台两账号不并发发布（错峰）；查重照常执行（风险 3 与账号数无关）。

**升级触发条件**（出现即启用完整策略）：

| 策略 | 适用 | 出口位置 |
| --- | --- | --- |
| `official-api` | 公众号等官方 API 平台 | multica edge（IP 白名单已报备，无关联风险） |
| `browser-local` | 浏览器自动化（视频号/抖音/小红书），**默认** | 本地 Mac：家庭 IP + 每账号独立 pw-profile |
| `browser-proxy` | 同平台 ≥3 账号做矩阵时 | 按账号绑定独立住宅代理，一账号一出口 |

发布调度遵守账号出口策略：`browser-local` 类执行实际跑本地（channels-verify 已具备），multica 只编排不执行。硬规则：同一出口 IP 并发同平台账号数为 1。

**防遗忘机制**（规则不能只躺在文档里，须系统提示）：

1. **加账号提示**：账号资产台录入/编辑账号时校验并提示。同平台第 2 个账号提示已达错峰上限；第 3 个起强提示"已进入矩阵规模，建议配置 `browser-proxy` 独立出口"——不阻断保存，但提示与是否采纳自动记入账本流水（出事时可追溯"系统提示过"）。
2. **驾驶舱巡检项**：账号健康区常驻"矩阵规模"状态行（如"抖音 2/3"），接近阈值变黄。日常巡检即可感知，无需记忆规则。
3. **周期复盘兜底**：周复盘 routine 固定带出各平台账号数与出口策略覆盖情况。

阈值与规则配置化，改阈值即决策记录。

### 2. 效果数据回流 → 数据巡检 + 账本对账

运营核心循环是 发布 → 数据 → 选题决策，通道①须扩展出效果数据流：

- multica 侧**数据巡检 SOP**（autopilot 编排，**双执行位**）：official-api 类账号（公众号）由云端 agent 直采；browser-local 类账号（抖音/视频号/小红书）登录态在本地，由本地 runner 实际抓取、经 multica API 写回报告 issue 走契约上行——multica 只编排，执行就近（与巡检 SOP 同一纪律）。结构化上行：账号/内容/曝光/播放/完播/互动/涨粉。报告格式契约：`tradewind/contracts/effect-report-v1.md`（两端唯一耦合点，变更须升版本）。
- paperclip 侧：效果流水入账本；驾驶舱加数据视图；**复盘对账视图**——决策记录与效果数据同轴，直接回答"这次放行的批次实际表现如何"。
- 数据异常即风控信号：账号数据骤降计入健康度，驱动熔断——发布流水、效果数据、健康度三者闭环。

### 3. 同质化 → 审批前查重预检

批量生成 + 多账号分发的经典死法是内容同质化被判定搬运（批内相似、跨批次自我重复、跨账号消重失败）。查重作为审批工作台预检步骤，且是**豁免放行的前置条件**（规则豁免必须查重通过；人审件标红提示但不阻断）。

**分工：生产内控在 multica，治理比对在 paperclip（与风险 2/4 同构：执行侧契约 + 通道①上行 + 治理呈现）。**

- **multica 批内自查（生产内控）**：生成管线内联，新生成件 vs 同批件，批内相似度超阈值直接反馈 prompt 加差异化变量**重生成**——废件不出厂，不进待审队列。通过件连同指纹（文案 simhash + 视频关键帧 pHash）随内容元数据契约上行，产物不过桥。
- **paperclip 历史比对（治理）**：插件存指纹库（`plugin.state`，跨批次发布史=治理资产），新件 vs 历史库判定绿/黄/红，emit `dedup-checked` 事件供审批工作台订阅；豁免前置硬校验，人审件标红不阻断。
- 单条路径内容本体在本地，指纹由插件本地计算后入同一指纹库。
- 默认阈值：文本相似度 0.9、视频 pHash 汉明距离 ≤ 8；用实际生成内容校准。阈值配置化，变更入决策账本。
- 命中记流水："此件与某批次某件相似度 0.93"——相似度与数据表现的相关性可反哺生成侧多样性控制。

### 4. 自动化脆弱性 → 巡检 SOP（multica）+ 健康治理（paperclip）

平台改版导致 playwright 选择器失效、批量任务全挂是常态（social-auto-upload 的 issue 区即前车之鉴）。

**分工：巡检执行在 multica 做 SOP，汇聚判定呈现留 paperclip。**

multica 侧 autopilot 例行任务（巡检 SOP）：

- **发布探测**：低峰期冒烟单条，验证发布链路可用。
- **登录态心跳**：定时验证各账号登录态（browser-local 账号由本地 runner 执行，multica 编排调度，执行按出口策略就近落位）。
- **平台改版探测**：定期校验发布页关键结构指纹（选择器存在性），改版在发布失败**之前**预警——从事后修复变事前预警。
- 发布失败分类随 dispatch-result 上报（选择器失效/登录态失效/风控拦截，三类三条处置路径）。

paperclip 侧（插件）：

- 汇聚失败分类 + 巡检报告 → 出口健康指标（滚动窗口成功率）。
- 阈值判定（< 70%）→ 降级标记 + 驾驶舱出口健康卡片告警。
- 降级模式：待发布件转人工队列（发布清单：内容引用 + 平台 + 账号 + 参数），人半手动发布；账号资产台标注"出口降级"，排期可见。
- 恢复：修复 → 冒烟单条 → 成功率回归 → 解除降级；修复动作记流水（长期形成各平台改版频率/修复耗时数据，评估自动化性价比）。

巡检报告格式契约已落：`tradewind/contracts/patrol-report-v1.md`。三份执行侧契约（effect-report / content-metadata / patrol-report，均在 `contracts/`）至此写齐，multica 侧 SOP 与 paperclip 侧解析器可并行开发。

现阶段最小实现：失败分类字段先进 dispatch-result；插件先只告警不自动降级（量小人工处置最优）；冒烟即单条发布流程，天然存在。

### 5. 选题/文案资产 → Obsidian 知识库本体 + Weknora 检索 + 账本记状态

文案资产（选题线、标题模板、爆款拆解、方法论）的打通与沉淀以知识库为本体：

```
素材本体层：Obsidian vault（git 同步，唯一事实源；obsidian-git 免费插件）
  benyue/media-assets/：选题线/（每线一页）、标题模板/、爆款拆解/、
  方法论/、复盘报告/（agent 写回，约定只写此目录）
检索层：Weknora（已部署，挂入 multica 作 agent 检索工具）
  生成 agent 语义检索素材："给我 3 个奖金盘点类高完播开头"
消费与治理：
  multica 生产 agent：Weknora 检索 + vault git 只读 clone 取模板
  paperclip 账本：只记选题线状态变更（新立/验证通过/放弃，含依据），
  与决策记录同构；素材本体不进账本
```

设计要点：

- **markdown+git 是同时服务人和 AI 的最薄媒介**：人在 Obsidian 拆解爆款即积累生产资产，无二次搬运；git 对云/本地/检索引擎天然多方可达。
- **同步**：vault 经私有远端同步，云侧 agent 只读 clone；复盘 agent 写回报告只进 `复盘报告/` 目录，与人写笔记不冲突。
- **版本即 git tag**：模板版本 = vault 路径 @ git tag，content-metadata 契约的 `prompt_ref` 采用 `vault://` 引用，溯源精确到版本。
- **生产门槛纪律**：RAG 检索会把未验证灵感当套路用——生成 agent 只消费**验证状态为"通过"**（以账本决策记录为准，vault 页面前言引用）的选题线/模板。
- 状态变更的触发方式：数据说话、agent 提案、人决策——effect-report 的 `above_baseline` 聚合 → 复盘 agent 评估选题线 → 走通道③④决策上行/拍板 → 入账本 + 更新 vault 状态。
- 打分机制与状态机细节**等产能验证有第一批真实数据后再定**，现在只定结构不定算法。

## 已实测的 Multica API 事实（2026-10-30）
